Troubleshooting mindset

How I approach a support ticket

A repeatable process keeps the investigation focused without losing sight of the person who needs help.

  1. 01

    Listen to the user and understand the real impact.

  2. 02

    Confirm the symptoms rather than relying only on the ticket description.

  3. 03

    Check the simplest and most likely causes first.

  4. 04

    Separate account, device, application and network issues.

  5. 05

    Test one possibility at a time.

  6. 06

    Resolve the root cause where possible.

  7. 07

    Confirm that the user can work again.

  8. 08

    Document the outcome clearly.

“The user may describe the issue as ‘Outlook is broken’ or ‘the printer is offline.’ My job is to turn that broad complaint into a specific problem that can be tested and resolved.”

Support Investigations

Evidence before assumptions.

Five examples of moving from a broad user report to a specific, verified outcome.

These investigations are based on common issues encountered and practised during my IT support internship, technical training and hands-on labs. Details have been generalised to protect user and organisational information.

User report “I changed my password yesterday, and now my account keeps locking.”

Repeated lockouts pointed beyond the account to stored credentials on a connected app or device.

  • Active Directory
  • Microsoft 365
  • Credential Manager
  • MFA

User report

“I changed my password yesterday, and now my account keeps locking.”

Why it mattered

The user needed reliable access to email and shared resources throughout the workday.

Initial thoughts

The account might be locked, the new password might not have synchronised, or another service might still hold the old password.

Investigation

After verifying the user, I distinguished a lockout from a mistyped password. I asked about Outlook, mobile mail, Wi-Fi, VPN, mapped drives and Credential Manager, then looked for repeated authentication attempts.

What changed my thinking

Unlocking restored access only briefly. When the lockout returned, the account itself was unlikely to be the cause; something else was repeatedly submitting stale credentials.

Root cause

A connected application or device continued authenticating with the old password.

Resolution

I updated or removed the stored credential, then unlocked the account once the repeated attempts had stopped.

Verification

The user signed in, opened Microsoft 365 services and continued working without another lockout.

Documentation

I recorded the affected credential source, checks completed, change made and successful sign-in test without recording passwords.

If I saw this ticket again tomorrow

I would ask about a recent password change and connected devices before repeatedly unlocking the account.

User report “Outlook keeps asking for my password, but the same password works online.”

A successful browser sign-in isolated the fault to the local Outlook client.

  • Outlook
  • Microsoft 365
  • Outlook Web
  • Cached credentials

User report

“Outlook keeps asking for my password, but the same password works online.”

Why it mattered

The user needed desktop Outlook access before an upcoming meeting.

Initial thoughts

The account was probably valid, but Outlook or Windows might be retaining an outdated token or password.

Investigation

I first tested Outlook Web. After that worked, I reviewed Windows Credential Manager and cached Microsoft 365 credentials, closed Outlook fully and restarted it. Profile recreation remained a later option.

What changed my thinking

Successful Outlook Web access meant this was not “the account cannot authenticate.” The scope narrowed to the desktop client and local cache.

Root cause

Outlook retained an outdated cached credential after the password change.

Resolution

I removed the stale credential and restarted Outlook so it could request and store a current sign-in token.

Verification

Outlook opened without another prompt and successfully sent and received a test message.

Documentation

I noted that web access worked, identified the cache as the local failure point and recorded the sign-in and mail-flow tests.

If I saw this ticket again tomorrow

I would test Outlook Web before repairing or reinstalling the Outlook application.

User report “The office printer says offline, but other people may still be able to print.”

Checking scope first kept the investigation on the affected workstation.

  • Windows 11
  • Print Spooler
  • TCP/IP
  • Drivers

User report

“The office printer says offline, but other people may still be able to print.”

Why it mattered

The user needed to print documents required that day.

Initial thoughts

If colleagues could print, the device and network path were probably available. The queue, spooler, port or driver on one workstation became more likely.

Investigation

I confirmed impact, power and network status, checked connectivity to the printer IP, reviewed “Use Printer Offline,” inspected the queue and restarted the Print Spooler. I verified the port and driver before considering reinstalling anything.

What changed my thinking

Other users could print. That evidence moved the fault away from the printer hardware and toward the affected computer.

Root cause

A stuck print job had left the local print queue and Print Spooler in an unresponsive state.

Resolution

I cleared the blocked queue, restarted the Print Spooler and returned the printer to its online state.

Verification

The user printed a Windows test page and then the required document.

Documentation

I captured the user-only scope, queue condition, spooler restart and successful test print.

If I saw this ticket again tomorrow

I would first establish whether the issue affects one person or the whole office before touching the printer hardware.

User report “The VPN is not connecting, and I need access to shared files from home.”

Testing ordinary internet access and another network separated the VPN from local DNS.

  • VPN client
  • DNS
  • MFA
  • Remote support

User report

“The VPN is not connecting, and I need access to shared files from home.”

Why it mattered

The remote employee needed access to shared files to continue working.

Initial thoughts

The issue could sit with internet access, credentials, MFA, name resolution, the local client or the VPN service.

Investigation

I confirmed normal browsing, checked whether others were affected, verified the device time, captured the exact error and checked credentials and MFA. Name resolution failed on home Wi-Fi but the connection worked through a mobile hotspot.

What changed my thinking

The hotspot test worked. That made a widespread VPN failure or damaged client unlikely and focused the investigation on the home network’s DNS path.

Root cause

The home router was supplying a DNS service that could not resolve the VPN gateway reliably.

Resolution

After confirming the organisation’s approved approach, I refreshed the network connection and used a working DNS configuration. No VPN profile rebuild was needed.

Verification

The VPN connected on home Wi-Fi, MFA completed and the user opened an authorised shared file.

Documentation

I recorded the exact error, comparison network test, DNS finding and successful resource-access check for future escalation context.

If I saw this ticket again tomorrow

I would confirm internet connectivity and capture the exact VPN error before changing the client configuration.

User request “A new employee starts Monday and needs their laptop, Microsoft 365 access and team resources ready.”

A role-based checklist connects the account, licence, groups, device and first-day handover.

  • Active Directory
  • Entra ID
  • Microsoft 365
  • Hardware setup

User request

“A new employee starts Monday and needs their laptop, Microsoft 365 access and team resources ready.”

Why it mattered

The new employee needed to be productive from their first morning.

Initial thoughts

Provisioning depended on an approved request with the correct role, manager, department, start date and access requirements.

Investigation

I confirmed approval, followed the naming convention, assigned the required licence and approved groups, prepared the updated Windows device and configured MFA, Outlook, Teams and printers. I checked shared drive, mailbox and SharePoint access and recorded asset details.

What changed my thinking

Onboarding is not one account task. A missed licence, group or permission can prevent the whole first-day experience from working.

Root cause

This was a planned service request rather than an incident; the main risk was an omitted dependency or unapproved access.

Resolution

I completed the role-based checklist, provided temporary credentials securely and prepared a clear handover.

Verification

The user and manager confirmed sign-in, MFA and access to the approved team resources.

Documentation

I completed the onboarding and asset records, including licences, approved group membership, applications and handover status.

If I saw this request again tomorrow

I would begin with a role-based checklist and compare access with an existing employee in the same team, while still obtaining proper approval.
